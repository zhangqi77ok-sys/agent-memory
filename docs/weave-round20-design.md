# 第二十轮设计：从「存点贴线」到「织网」（工程化落地）——已落地

用户要求（2026-10-24）：反思的 6 项不足全部完成；另有硬指标——
单用户千万级记忆，简报 50ms 以内。两条线并行：深度在后台长，
速度在前台保；深度计算一律不进简报路径。

## 第一阶段（已写，不碰现有文件，全套不受影响）

- `app/graph_stats.py`：只读计算。节点 = 有效事实 + 经验；合作图 =
  supports / refines / generalizes / related；contradicts 只报张力，
  不进合作图（矛盾边连起来的不是共识簇）。输出：节点/边数、密度、
  孤儿（无任何有效边）及孤儿率、枢纽 top-k、合作社群（并查集）、
  桥（迭代 Tarjan，边数 > 200k 时跳过并明说）、矛盾张力及是否同社群。
- `app/edge_learning.py`：纯规则。应用 +0.10 靠拢（`s += (1-s)*0.10`）、
  否决 ×0.90、闲置每月 ×0.95，下限 0.10；`find_spread_edge` 双向查
  扩散边（对称关系规范化存储，有向关系只存一个方向，故双向都要查）。
- `tests/test_round20_graph.py`：三角 + 链 + 矛盾边 + 孤儿的标准图，
  断言社群/桥/枢纽/孤儿/张力与边学习规则。

## 第二阶段（已落地，十八、十九轮提交合并后接线）

1. **边学习接线（已落地）**：迁移 0020 新增 `brief_delivery_edge`（delivery_id、
   link_id、insight_id、applied）+ `memory_link` 的 (app_id, user_id)
   复合索引（现只有 user_id 单索引，千万级下按用户扫边会慢）+
   `memory_link.decayed_until`（闲置衰减结清锚点，同一段闲置只扣一次）。
   简报扩散时记边；任务回流 / 人工反馈给经验记应用时顺着交付记录
   调边权（成功加、失败减、部分只记账不改权）；巡逻任务每月对长期
   零交付的边结算闲置衰减。测试：tests/test_round20_wiring.py。
2. **网度量接口（已落地）**：`GET /v1/me/graph/stats` + MCP `memory_graph_stats`
   + 面板「网结构」一节（GraphStatsPanel：计数、密度、孤儿率、张力、
   枢纽、社群、桥）。千万级下该接口是离线快照口径，不承诺 50ms；
   50ms 只约束简报路径。连接度量口径见 docs/eval.md 第二十轮一节。
3. **织网简报（已落地）**：`BriefResponse` 加 `graph` 段——本批胜出条目之间的
   诱导子图边（查 `memory_link` 两端都在胜出集内）+ 每条的 linked_from
   路径。REST 与 MCP 简报都带 graph 段；无记忆时的早期返回无 graph。
4. **矛盾综合（已落地一半）**：裁决改规则——输家若有 distinct 的 `applies_when`
   且有证据，不退役，改为「条件分化」保留（`applies_when` 即其条件），
   并与胜家连一条 `related` 边标注分化；只有同条件且证据更弱时才
   退役。综合节点（起草一条陈述适用条件的原则洞见并把两边连到它下面）
   不在本轮——模板硬编自然语言不可取，等 LLM 起草通道稳定后做，
   列入后续人脑化轮次，不算第二十轮欠账（设计时即已说明）。
5. **抽象阶梯（已落地）**：`kind="principle"` 的原则层经验（提炼 kind 扩展，
   提示词版本 distill-2026-10-v4）+ 简报原则带支撑：胜出的原则经
   generalizes 边带出 ≤2 条泛化支撑经验（reason=principle_support，
   同项目优先、置信度降序、受 token 预算 skip-not-break 约束）。
   支撑是脚注：不占 k 名额、不进交付 insight_ids、不记交付边
   （回流只给原则记账，人工反馈不归因到脚注）。常规候选仍按原流程
   补齐 k；原则本身作为普通候选参与竞争，不设单独门控。
6. **连接度量验收（已落地）**：网密度、多跳使用率（扩散带出且被应用的
   占比，`brief_delivery_edge.applied` 可算）、孤儿率三项进 docs/eval.md，
   与 50ms 规模压测同一轮交付。

## 50ms 千万级验收（已落地，1M 实测 + 模型外推）

- PG 上灌 100 万行真实分布语料（32 主题 Zipf，5230 万倒排行）实测：
  精确探针 top p50 7895.2ms → 候选上限 2000 后 1065.4ms →
  锚点探针 CAP=100 + 置顶臂部分索引修复 + 批量 use_count +
  非文本更新跳过倒排同步后 **top p50 39.6ms、mid p50 44.6ms**（k=5，
  iters=20）。p95 / max：top 78.1ms / 124.0ms，mid 58.2ms / 59.9ms——
  p95 超标是本机磁盘 fsync（单次 commit 稳定约 20ms）与冷页缓存的噪声，
  p50 与 p95 分开报告，不拿 p50 冒充全分位达标。
- 设计路线修正（实测证据在 docs/eval.md）：原计划「按词频从稀有词开始
  求交」被否决——top 查询最稀有在库 token「处理」DF=8430，但它的行
  命中数全是 1，过不了门槛，稀有锚点交出空集；改走锚点采样
  （查询词序取锚 + LATERAL 精确验数 + 找不够回落精确探针），
  因此也不需要为排序单独建 DF 表（查询词序已够选锚，DF 表的
  写入维护与回填成本省下了；若将来查询分布变化使词序锚失效，
  再评估 DF 表）。
- 本机（2 核 / 7.7G）实灌千万级不现实：1M 实测 + 模型外推是诚
  实口径，报告里明说，不伪造千万级实测数。外推模型：简报耗时 =
  O(CAP) 采样验数 + O(CAP) 取行打分 + O(1) 记账 commit + 缓存效应，
  与总量、命中桶大小无关；1M→10M 时 p50 应维持同量级，p95 拖尾
  随冷缓存缺页率变长（见 docs/eval.md 外推一节）。
- 播种教训：倒排 COPY 前先卸索引、写完重建，1M 播种从 3 小时以上
  压到 445 秒；VM 替换两次打断播种（单事务回滚），提速本身就是
  缩小被打断窗口的手段。
