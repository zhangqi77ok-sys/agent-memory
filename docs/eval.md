目标：证明记忆服务「记得住、记得对、会过期、不串人」。任一失败即阻断合并与发布（Jenkins `Lint & Test` 阶段）。

```bash

pytest -q                 # 全部
pytest -q -k cross_user   # 只跑串用户
```

| 类别 | 测什么 | 判定 | 当前用例 |

| 记住了吗 | 同意后写入，Worker 抽出的事实能在列表、导出和召回里看到 | 列表 `total≥1`，导出含该事实 | ✅ `test_consented_write_is_extracted_into_list_and_export` |

## 中文陪伴场景基准评测（50 条基准集，F1 门禁）
评测用例位于 `tests/test_eval_benchmark.py`，专门覆盖中文陪伴场景真实分布：
1. **用户偏好（Preference）**：饮食、作息、昵称、运动休闲习惯。
2. **事实更新（Fact Update）**：工作变动、宠物更新、居住地址变更，确保新版本覆盖旧版本且旧版本不被召回。
3. **否定与禁忌（Negation）**：过敏源、忌口食材、社交与剧透禁忌。
4. **多轮深层事实（Multi-turn）**：家人纪念日、母校、长远梦想等深层陪伴细节。
5. **过期失效（Expiration）**：短期状态与预约（`valid_to` 不为空），确保已过期事实 0 泄露。

**CI 质量门禁指标**：
- 召回覆盖率（Coverage / Recall） >= 80%（当前实测 100.00%）
- 检索准确率（Precision） >= 80%（当前实测 100.00%）
- 过期数据泄露率 = 0%（当前实测 0%）
任何低于门槛的变动将在 CI 阶段直接阻断构建。

## 经验记忆评测（50 例，E 门禁，第四轮补建）

评测用例位于 `tests/test_eval_experience.py`，与事实基准分工：那边考「事实记得准不准」，这边考「过程 → 经验 → 下一次更便宜」整条闭环。五类各 10 例，另有计数门禁 `test_gate_case_counts` 逐类点名，少一例即红。全部离线确定性运行（假提炼器/假嵌入器），判定口径如下：

| 类别 | 测什么 | 判定 |
|---|---|---|
| A 提炼产出 | 失败/重试/高成本/平凡/多产出轨迹、空内容与非法类型候选、向量与审计落盘 | 经验条数、kind、来源 episode、version、audit 记录与预期一致；平凡轨迹产出为 0 |
| B 安全门 | 轨迹与候选里的密钥：`sk-`、Google key、`ghp_`、eyJ 三段式令牌、Bearer、连接串口令、`password=` 键值对；注入候选与轨迹注入句 | 送提炼器的原文与入库内容中密钥原文 0 出现、占位符在位；注入候选被拦下，轨迹注入触发短语在送模型前被剥离 |
| C 去重与更新 | 同主题同内容、换内容、包含式主题、形近主题、同批重复、三次连续更新、残留重复行、换 kind、跨用户 | NOOP 不新增、UPDATE 版本 = 历史最大版本 + 1 且旧行全失效、形近不误合并、用户间不互串 |
| D 情境召回 | 经 applies_when / 内容 / 向量三路命中；无关任务、正交向量、低于余弦门槛、k 上限、排序、已失效、跨用户 | 该命中的命中（hybrid 需 reason 标注）、不该命中的为空，余弦门槛沿用 COS_MIN 0.66 |
| E 任务表现 | 10 个脚本化场景（端口探测、退避重试、缓存优先、查磁盘、先看日志、设超时、分页、套模板、迁移前备份等）走完整闭环后对比有/无简报 | 有简报时 token 严格更低、失败不更多；E01 与演示脚本同数（400 → 130，省 68%） |

**门禁指标**：50 例全过（当前实测 50/50，另计数门禁 1 例）；B 类密钥原文泄露 = 0。
**已知边界**：密钥脱敏只认已知形状，任意格式的自造密钥仍可能漏过（规则脱敏的固有边界，靠 B 类用例盯住已覆盖的形状）；E 类是脚本化策略，证明管线与记账，不代表真实 LLM 提炼质量，真实收益需接真实 Agent 对照跑。

## 信任质量评测（第十六轮「信任三件套」）

`tests/test_round16_trust.py`（16 例）：信任不是口号，是账。考四件事——**回流结账**（简报交付落账、任务成功/失败/部分完成分别记 applied 与半权 auto 信号、置信度按 (1+pos+0.5·auto_pos)/(2+pos+neg+0.5·(auto_pos+auto_neg)) 重算、同一份交付只结一次、项目不符不结、经验已换版时功过记给接棒的新版本）；**证据校验**（解析层保留 evidence、逐字引文验过标 verified、编造引文与无引文都带未验证标入场、未验证经验简报排序打折但在场且标记可见）；**矛盾裁决**（有 contradicts 边且置信差 ≥0.30、胜方证据 ≥2 才关负方并关边；差距不足不裁；置顶的负方永不自动裁）；**真遗忘**（闲置 >180 天、从未应用、从无正面证据的经验关行；被应用过/被好评过/新鲜的都不动）。

## 简报延迟基准（第十二轮建，第十四轮复测，第十四轮补完再测）
`scripts/bench_brief.py`，SQLite + 纯关键词路径（无嵌入服务），环境为 2 vCPU 容器，仅作量级参考。语料分两种：典型语料 = 10 个主题各有独立词汇（真实提炼出的经验按主题天然分散）；最坏语料 = 第十二轮的原始造数（全行共用同一套模板正文，固定查询与每行都共享 bigram，全员过关键词门槛）。

典型语料：

| 经验条数 | p50 | p95 | max |
|---|---|---|---|
| 100 | 4.4ms | 5.0ms | 13.6ms |
| 1000 | 6.8ms | 7.3ms | 9.4ms |
| 5000 | 19.4ms | 21.5ms | 69.6ms |

最坏语料：

| 经验条数 | p50 | p95 | max |
|---|---|---|---|
| 100 | 5.2ms | 5.6ms | 13.4ms |
| 1000 | 19.1ms | 21.8ms | 59.9ms |
| 5000 | 82.4ms | 132.7ms | 147.1ms |

历史数字：第十二轮（全表打分、无通道）5000 条 185.6ms（语料即现在的「最坏」）；第十四轮第一版（关键词门槛下推 SQL 的 LIKE 计数）典型 5000 条 78.2ms、最坏 150.4ms。

读法（补完）：第一版的 78.2ms 曾被判为「无文本索引时的地板」——复查时逐段剖析推翻了这个判断：纯作用域扫描只要 4ms，真正的地板是逐行 × 逐 token 的子串匹配（约 14µs/行），换 instr、先拼文本、子查询物化都在 62–90ms 徘徊。补完改倒排索引：每行的 token 集合落表（`memory_insight_token` / `memory_fact_token`，由 ORM 事件与父行同事务维护，迁移 0014 回填存量），召回探针两段式取数——先只在倒排表内按 (token, id) 索引数出过门 id，再按 id 回父表取列（一段式 JOIN 的计划不可控，SQLite 实测会选成按用户扫父表逐行回探，58ms）。倒排存的正是打分文本的 token 集合，COUNT 出的命中数与逐行 kw_score 的分子严格相等（等价性有性质测试守着），探针行不必再逐行打分。结果：5000 条典型语料 p50 **19.4ms**，第十二轮立的「<30ms」目标达成；1000 条以内约 7ms，规模敏感性基本消除。最坏语料的 82.4ms 是另一回事：全员真命中时，任何精确实现都要把 5000 条真候选搬出来逐条算排序分（实测取数约 33ms + 打分约 26ms），那是 O(命中数) 的地板，不是索引失效——真实语料不会长这样，保留这个数字是为了不只报好看的。写入侧代价：每行多维护约 50 条倒排记录（同事务 executemany），单行写入亚毫秒级；简报记账这类非文本更新只多一次索引比对、不重写。Postgres 侧向量分支维持「距离过线 + 按距离排序 + LIMIT 200」走 HNSW 的形态（第十四轮 EXPLAIN 结论不变）：真库实测走 ix_insight_hnsw / ix_fact_hnsw 的 Index Scan；过线行超过 200 时更远的会被截掉，关键词与置顶分支不受影响，SQLite 路径保持全量精确。

### 排序乘子敏感性（scripts/ranking_sensitivity.py，200 条合成经验）

| 变体 | top-5 Jaccard | Kendall tau |
|---|---|---|
| 置信乘子关掉（0.7+0.6c → 1.0） | 0.111 | 0.853 |
| 置信乘子加倍陡峭（0.4+1.2c） | 0.667 | 0.861 |

### 10 万行简报压测（scripts/bench_brief.py --sizes 100000）

## 第二十轮：连接度量与 50ms 规模验收（PG，1M 行实测 + 模型外推）

### 连接度量（定义与口径，取数口径见 GET /v1/me/graph/stats）

除 token 节省与命中率外，第二十轮验收加三项——网的深浅本身要可量：

- **网密度** = 2E / (V(V-1))，V = 有效事实 + 经验节点数，E = 合作边数
  （supports / refines / generalizes / related；contradicts 只记张力不进 E）。
  分母含孤儿节点——孤儿故意稀释密度，密度低首先说明网没织起来，
  不是说明边少。标准图（三角 + 链 + 矛盾边 + 孤儿，tests/test_round20_graph.py）：
  V=7、E=5、密度 10/42 ≈ 0.2381。
- **孤儿率** = 孤儿节点数 / V，孤儿 = 无任何有效边的节点。标准图：1/7。
  孤儿率高说明大量记忆从未被连进网——织网巡逻与提炼连边要先找它们。
- **多跳使用率** = 扩散带出且被应用的交付边 / 全部扩散交付边，即
  `brief_delivery_edge` 中 applied 的行数占比（交付边只对 reason='linked'
  的扩散胜出者记，applied 由任务回流 / 人工反馈结账时标）。
  另一口径：扩散应用数 / 全部应用数（应用价值里多跳占几成）。
  这项量的是「线」有没有被走通——边只画不用，多跳率就是 0。
  三项都由 `compute_graph_stats` + 交付边表直接算出，不靠抽样估计。

### 1M 行简报压测（scripts/bench_brief_pg.py，PG 真库，本机 2 核 / 7.7G）

语料：32 主题 Zipf 分布（topic 0 约 24.6%），100 万条经验 + 5230 万倒排行，
倒排表总计约 10GB；查询 top =「部署服务时端口被占用怎么处理」
（命中桶 342150）、mid =「缓存被打穿热点重建怎么办」（命中桶 164030），
纯关键词路径（无嵌入服务），iters=20，简报 k=5。

| 阶段 | top p50 | mid p50 | 说明 |
|---|---|---|---|
| 精确探针（无上限） | 7895.2ms | 2449.0ms | 耗时 ∝ 命中桶，不 ∝ 总量 |
| + 候选上限 2000（命中数倒序截断） | 1065.4ms | 497.4ms | 截断不够：stage-1 聚合本身占主导 |
| + 锚点探针 CAP=100、置顶臂部分索引修复、批量 use_count、非文本更新跳过倒排同步 | **39.6ms** | **44.6ms** | **达标（p50 < 50ms）** |

p95 / max（同一轮）：top 78.1ms / 124.0ms，mid 58.2ms / 59.9ms。
p95 超标是本机环境的噪声地板，不是算法回退：单次 commit 的 WAL fsync
在本机磁盘上稳定约 20ms（实测 p50 20.1ms，flush 本身仅 0.3ms），
外加冷页缓存的随机缺页；生产 SSD 上 commit 约 1–3ms，p95 会显著收窄。
报告里 p50 与 p95 分开写，不拿 p50 冒充全分位达标。

### 为什么不是「稀有词先求交」（设计路线的实测修正）

原计划是按词频从最稀有词开始求交。实测否决了它：top 查询 13 个 token
里实际在库的只有 5 个，最稀有的「处理」DF=8430，但它的行命中数全是 1
（另一主题），过不了 ≥2 的门槛——稀有词锚点会交出空集；真正过门槛的
244580 行全是命中数恰好 4 的行，且恰好等于「占用」/「端口」任一 token
的 posting 集合。稀有优先在这里既找不到胜出者，也省不下扫描。
改走的路线是**锚点采样**（app/recall.py `_anchor_probe`，仅 PG）：
按查询词序逐个取锚，每锚取前 CAP 条 posting（UUID 序≈随机样本），
LATERAL 按主键索引逐行验跨全部 token 的精确命中数，累计过门行 ≥ CAP
即停；找不够 CAP 时回落精确探针（正确优先，慢只慢在罕见情形）。
配套的三处修补同样是实测逼出来的，缺一不可：
- 置顶臂 `pinned IS TRUE` 认不出部分索引 `WHERE pinned` 的谓词，
  1M 行下从索引扫描 0.014ms 退化成并行全表扫描 210ms——改裸 `pinned`，
  谓词对上即回索引（SQLite 侧裸列即 0/1 判断，语义等价）；
- 赢家 use_count 从 k 次逐行 UPDATE + k 次 after_update 事件
  （每次先查现存 token 集）合并为一条批量 UPDATE；
- 非文本更新（use_count、反馈计数）跳过倒排同步：文本属性一个没动时
  token 集必然没变，判定失败时回落同步（宁可多查，不可漏同步）。
胜出质量对照：锚点版与精确版胜出分数逐字相同（top 全 0.3077 = 4/13，
mid 全 0.6364 = 7/11，reason 均为 keyword；平分数据里主语不同只是
244580 个平分行之间的任意取舍，分数才是 agent 消费的东西）。

### 千万级外推模型（诚实口径，不伪造千万级实测数）

本机实灌千万级不现实（播种 1M 已占 10GB，千万级约 100GB 且播种窗口
内两次被 VM 替换打断；1M 实测 + 模型外推是诚实口径）。
成本模型：简报耗时 = O(CAP) 锚点采样验数 + O(CAP) 取行打分
+ O(1) 记账 commit + 缓存效应，与命中桶大小无关——锚点扫描是带 LIMIT
的索引寻址，验数是按 id 的主键切片，取行是 CAP 行主键点查，
没有一项随总量或桶大小增长。因此 1M→10M 时 p50 应维持在同一量级；
会变差的只有冷缓存缺页率（数据 10 倍于内存时 p95 拖尾变长），
p50 不变、p95 变宽是模型给出的预期，不是事后解释。
播种本身也留了一条工程教训：倒排 COPY 前先卸索引、写完重建，
1M 播种从 3 小时以上压到 445 秒——逐行维护 5230 万行两棵 B 树
是原版播种跑不完的主因（见 scripts/bench_brief_pg.py 的注释）。

## 第二十一轮：睡眠巩固度量（巡检报告口径）

睡眠巩固不进简报路径，它的验收口径就是巩固报告本身
（GET /v1/me/consolidation/latest，表 consolidation_report）：

- **合并数 merged**：本轮合并的近重复事实对数。事实此前没有合并巡检，
  睡眠是第一条事实合并通道；合并后保留行的佐证数 = 两行之和、置信度
  按 support/(support+1) 重算，边按 migrate_links 迁移。
- **剪边数 pruned**：本轮关闭的死边数。死边定义是三条同时满足：
  强度到下限 0.10、闲置 ≥ 3 整月、从未被证实应用过——只看其中一条
  都会误伤（刚被否决到下限但最近还在用的边、闲置但强度未到下限的边
  都不剪）。关边可逆：日后织网补边能重新连上。
- **强化数 strengthened**：本轮按共用证据加权的边数。窗口 = 自上次
  报告以来新产生的简报交付，同一段共用历史只结一次账；每边每轮只加
  一次（复用 strength_on_applied，与回流/反馈同规则）。
- **新建共用边 linked**：全量同现 ≥ 2 次且此前无任何有效边的经验对数，
  每轮上限 50 条，按同现次数降序。
- **抽象原则 generalized**：本轮从共用簇起草的原则数。簇门限：规模
  ≥ 3、跨 ≥ 2 项目、无现成原则覆盖 ≥ 2 名成员；无判定器时为 0，
  不硬编自然语言；每轮上限 5 个簇。
- **水位语义**：报告行每用户每轮都落（含全零行），零行就是下一轮的
  共用窗口起点——报告表既是展示物也是水位表。

## 第二十二轮：遗忘曲线度量（艾宾浩斯式衰减 + 复述增强）

遗忘不是“时间到了就删”，是置信度按闲置与复述有规律地走：

- **锚点对账**：day 0 用过、day 40 首扣 1 块、day 70 续扣 1 块、day 100
  续扣 1 块，合计 3 块 = 旧单次口径 day 100 的 (100-1)//30——锚点修掉
  的是每小时重复计费，不改总额口径。同一时刻重跑不再扣（锚点已到 now）。
- **复述因子**：月因子 = 1 - 0.05/(1 + applied_count + feedback_pos)。
  60 天闲置、0 次复述：0.5 → 0.475；4 次复述：0.5 → 0.495。
  曝光 use_count 不算复述，auto_pos 已含在 applied_count 里不重复计。
- **边基线对齐**：60 天前建的边，近期交付但未应用 → 仍衰减 2 个月
  （0.9 → 0.81225）；近期应用 → 跳过。曝光不再重置边的遗忘时钟。
- **前后召回变化**：同一条闲置 100 天的经验，consolidate 前后的简报
  分数下降（置信度 0.5 → 0.4287，排序乘子 1.0 → 0.957）；昨日刚被应用
  的经验分数不变。分数变化只来自置信度衰减——新近性按最后使用/生效
  算，consolidate 不动它，故前后可比。
- **退役线不动**：180 天真闲置线仍按自 last_used_at 起的真闲置算，
  不受衰减锚点影响；锚点只管置信度怎么扣，不管记忆何时退出召回。

## 第 23 轮：事实级反馈 API（迁移 0023）

- 事实/偏好置信度公式统一为 (S+P)/(S+P+N+1)（S = 佐证、P = 好评、N =
  差评）：无反馈时恒等于旧佐证公式 S/(S+1)，旧行数值不动；好评如一次新
  佐证（S=1 时 0.5 → 0.667），差评拉低（→ 0.333），正负相抵回 0.5。
- 接口与经验反馈同形：POST /v1/facts/feedback、POST /v1/preferences/feedback
  + MCP memory_fact_feedback / memory_preference_feedback；跨用户、不存在、
  未同意一律 404 / not_found，不泄露存在性；每次反馈记审计。
- 一致性修补：worker._bump_support 改用新公式——否则反馈后一次新佐证会
  把负反馈洗掉（S=1,N=1 时 0.333，佐证到 S=2 后旧算法给 0.667、新算法
  给 0.5）。事实没有扩散边与闲置时钟，反馈只动置信度，不碰边权、不刷
  时间。
- 前端：记忆行加 有用/无用 按钮（点后重载，置信徽标即时动）；列表项
  带出 feedback_pos/feedback_neg。
- 验证：新增 tests/test_round23_fact_feedback.py 14 例（公式恒等、事实
  好评/差评/高佐证/相抵、跨用户与不存在、审计、偏好、佐证保留反馈、
